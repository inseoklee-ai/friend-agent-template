## 섹션 1 — 시작 상태

**한 일** 시작 상태 다섯 가지를 확인하고, 오류 분석에 쓸 트레이스를 평가 데이터로 모았다.
**결과** 다섯 가지 모두 통과. 트레이스 154개, 평가 메시지 56건 전송 성공. 한 턴 $0.000336.

### 실습

| 필요한 상태 | 결과 |
| --- | --- |
| 로컬 실행 | `python -c "import app.main"` ok. provider=openai, model=gpt-4o-mini |
| 실제 LLM 키 | `LLM_PROVIDER=openai` — fake 아님 |
| Langfuse 키 | 세 개 모두 있음 |
| 단계별 계측 | 어제 완료. `chat-turn` 아래 `safety`, `choose-tools`, `tool:*`, `reply`, `memory-update` |
| 트레이스 30개 이상 | **154개** |

교안이 요구한 "도구 선택의 인자"와 "도구 실행의 결과"가 둘 다 남아 있다. 어제 `choose-tools` 에 고른 도구·인자·확신도·`decided_by` 를, `tool:<이름>` 에 인자·결과 요약·`ok` 를 남겼다.

`scripts/send_eval_messages.py` 를 만들어 `data/eval/` 의 메시지 56개를 로컬 서버로 보냈다.

```
보냄 56 / 실패 0
한 턴 $0.000336   (3건으로 먼저 재고 전체를 보냄)
```

### 결과

환경별 트레이스 수:

| environment | chat-turn | 비고 |
| --- | --- | --- |
| `default` | 49 | 중첩이 깨져 있던 때. `environment` 를 붙이기 전이라 기본값으로 들어갔고, 부모를 잃은 자식들도 루트로 섞여 있다 |
| `local` | 23 (+56) | 속성을 붙인 뒤의 로컬 |
| `staging` | 24 | staging |
| `repro`, `score-test` | 8 | 어제 재현·점수 시험용 |

### 문제점과 해결

**`.env` 가 `AUTH=supabase` 라 토큰 없이 `/api/chat` 을 치면 401 이다.** 서버를 로그인 없이 띄워야 한다.

```
$env:AUTH="none"; $env:STORAGE="memory"; uvicorn app.main:app --port 8080
```

`STORAGE=supabase` 는 `AUTH=supabase` 와만 쓸 수 있어서 저장소도 메모리로 바꾼다. 스크립트는 401 을 만나면 그 줄을 찍고 **바로 멈춘다** — 56건을 다 날리지 않기 위해서다.

### 기타

`default` 49개는 **섞어 쓰면 안 된다.** 실패를 셀 때는 `environment` 로 `local` 과 `staging` 만 골라야 한다. 안 그러면 한 턴이 여러 번 세어진다.

## 섹션 2 — 트레이스 읽고 실패 유형 만들기

**한 일** 날짜 관련 세 대화를 세 번씩 보내 단계별로 읽고, 도구 선택 평가 41건을 두 번 돌렸다.
**결과** 실패 유형 8개와 판정 기준 문장. 같은 평가 두 번에 36/41, 35/41 로 **틀린 항목 구성이 달랐다**.

### 실습 — 읽는 순서

```
② 도구 선택의 인자  →  ③ 도구 실행의 결과  →  ④ 답 만들기의 입력과 답
```

**처음 틀린 단계 하나만** 적는다. 앞 단계가 틀리면 뒤 단계는 맞게 동작해도 틀린 답이 나온다.

오류 분석의 규칙 둘:

- **유형을 미리 정하지 않는다.** 먼저 읽고 한 줄씩 메모한 뒤 비슷한 것끼리 묶는다. 미리 정한 지표가 있으면 거기 맞는 실패만 눈에 들어온다.
- **읽을 트레이스에 무작위를 섞는다.** 별로예요·신고가 붙은 것만 읽으면 사용자가 표시하지 않은 **조용한 실패**를 놓친다.

### 결과 — 세 대화 (2026-11-03 화요일 기준)

**"다음 공휴일 언제야?" — 처음 어긋난 단계: 도구 선택의 인자**

3번 모두 `from 2026-11-03, to 2026-11-30` 으로 이번 달까지만 잡았다. 다음 공휴일 12월 25일이 기간 밖이다. 도구는 "공휴일이 없습니다"라고 **맞게** 답했다.

| 실행 | 답 | 문제 |
| --- | --- | --- |
| 1 | "다음 공휴일은 11월 15일 수능날" | 도구 결과에 없는 날짜. 수능은 공휴일도 아니다 |
| 2 | "2026년 이후로는 나와 있지 않아" | 조회하지도 않은 기간을 단정 |
| 3 | "다음 공휴일은 12월 25일 크리스마스" | **답은 맞지만** 도구 결과에 없는 정보. 운 좋게 맞았다 |

**"12월에 연휴 있어?" — 도구 선택(중복) + 답 만들기(연휴 판정)**

`get_holidays` 를 3번 모두 두 번씩 불렀다. 답은 "연휴는 없지만"처럼 갈렸다. 도구가 요일(`12월 25일(금)`)까지 줬으므로 연휴 여부는 답 만들기가 따질 몫이다.

**"금요일 시험 전날 밤에 일찍 자라고 알려 줘" — 도구 선택의 인자**

| 실행 | `due_at` | 판정 |
| --- | --- | --- |
| 1, 2 | `2026-11-05T21:00` (목) | 맞음 |
| 3 | `2026-11-06T21:00` (금) | **틀림** — 전날이 아니라 당일 |

3번은 답도 "금요일 밤 9시"라 일관되게 틀렸다. **답만 보면 그럴듯해 트레이스 없이는 못 잡는다.**

### 결과 — 실패 유형표

| # | 실패 유형 | 개수 | 판정 기준 문장 (통과 조건) | 판정 방법 |
| --- | --- | --- | --- | --- |
| 1 | 도구 인자의 기간이 좁아 다음 공휴일이 빠짐 | 3/3 | 기간을 말하지 않은 공휴일 질문은 다음 공휴일이 들어가는 기간을 조회한다 | 코드 |
| 2 | 도구 결과에 없는 날짜를 말함 | 3/3 | 답에 나온 공휴일 날짜는 모두 도구 결과에 있다 | LLM 심사 |
| 3 | 연휴를 잘못 말함 | 2/3 | 공휴일이 금요일이나 월요일이면 주말과 이어져 사흘을 쉰다고 말한다 | LLM 심사 |
| 4 | 같은 도구를 중복 호출 | 3/3 | 한 턴에 같은 도구를 같은 인자로 두 번 고르지 않는다 | 코드 |
| 5 | "X 전날"을 X 당일로 저장 | 1/3 | "X 전날"은 X의 하루 앞 날짜로 저장한다 | 코드 |

| 7 | 도구를 써야 하는데 안 씀 | 1/41 | 날씨·미세먼지·공휴일을 묻는 말에는 해당 도구를 고른다. 에둘러 묻는 말도 포함 | 코드 |
| 8 | 상대 날짜·시각 표현을 잘못 계산 | 2/41 | "모레"는 오늘 +2일, "아침"은 08:00 으로 잡는다 | 코드 |

우선순위는 개수만으로 정하지 않는다. 2번은 사용자가 그대로 믿고 움직일 수 있어 피해가 크다. 4번은 답을 틀리게 하지 않지만 비용과 지연에 바로 나타난다.

### 문제점과 해결

**`record_usage` 가 트레이스 밖에서 오류 줄을 41번 찍었다.**

```
Context error: No active span in current context. Operations that depend on an active span will be skipped.
```

`scripts/eval_tools.py` 는 `model_choose` 를 직접 불러 `choose-tools` 관찰 단위 밖에서 돈다. 그런데 `app/llm.py` 가 호출마다 `tracing.record_usage()` 를 부르고, 그 안의 `update_current_generation()` 이 열린 span 을 못 찾았다.

`get_current_trace_id()` 로 확인하면 **같은 오류 줄이 또 찍히므로**, OpenTelemetry 의 span context 로 조용히 본다.

```python
def _in_span():
    from opentelemetry import trace as otel_trace
    return otel_trace.get_current_span().get_span_context().is_valid
```

섹션 3 에서 데이터셋을 돌릴 때도 같은 자리를 지나므로 미리 고쳤다.

## 섹션 3 — 데이터셋과 평가자

**한 일** 지금 평가가 못 잡는 실패를 잡게 하고, 데이터셋 네 개와 LLM 심사를 만들어 첫 실험을 돌렸다.
**결과** `holiday-reply` 12개 신설, `holiday-reply-judge` 설정, 같은 설정 두 번에 9/12·7/12.

### 실습 — 고치기 전에 잴 방법부터

고친 뒤에 무엇을 보고 "고쳐졌다"고 말할지부터 정한다. LLM 은 같은 메시지에도 실행마다 답이 달라서, 대화창에서 두세 번 맞았다고 고쳐진 것이 아니다.

지금 평가가 잡는 것과 못 잡는 것:

| 실패 | 지금 평가에서 | 이유 |
| --- | --- | --- |
| 시험 전날이 아닌 날로 저장 | **잡힘** | T34 에 `expected_args` 로 `due_at` 이 적혀 있다 |
| 다음 공휴일을 못 찾음 | 안 잡힘 | T26 은 `expected_args` 가 `{}` 라서 도구만 고르면 통과 |
| 도구 결과에 없는 날짜를 말함 | 안 잡힘 | 답에서 생기는 실패. 이 평가는 도구 선택까지만 본다 |
| 연휴를 잘못 말함 | 안 잡힘 | 이것도 답에서 생기는 실패 |

**평가는 정답에 적어 둔 것만 채점한다.**

### 실습 — T26 고치기

기간을 기대 결과에 **그대로 적으면 안 된다.** 인자를 비워 도구가 1년을 찾게 하는 것도 올바른 방법이라 맞는 답까지 틀렸다고 센다. 확인할 것은 "그 기간 안에 다음 공휴일이 들어가는가" 하나다.

```json
{"id": "T26", "expected_args": {}, "expected_covers": {"get_holidays": "2026-12-25"}}
```

`scripts/eval_tools.py` 에 `covers_match()` 를 더했다.

```python
if not start and not end:
    return []                      # 비워 두면 도구가 1년을 찾는다
if (start or "0000-01-01") <= want <= (end or "9999-12-31"):
    return []
```

바로 잡혔다.

```
T26 다음 공휴일 언제야?  →  기간에 2026-12-25 가 빠짐: from 2026-10-12, to 2026-10-31
```

### 실습 — holiday-reply 데이터셋

답에서 생기는 실패는 메시지를 처음부터 실행하면 못 가린다. 도구 선택이 고른 기간에 따라 도구 결과가 매번 달라져, **답 지시문 탓인지 도구 결과 탓인지** 알 수 없다. 그래서 도구 결과를 문장으로 **고정해** 넣고 답만 만들게 한다.

`data/eval/holiday_reply.jsonl` 12개(실패 사례 7, 정상 사례 5).

| id | 메시지 | 고정한 도구 결과 | 통과 조건 | 종류 |
| --- | --- | --- | --- | --- |

답의 실패를 LLM 심사에 맡기는 이유는 **맞는 표현이 여러 가지**이기 때문이다. 연휴는 "사흘 쉴 수 있어", "주말까지 쭉 쉬네"로 다 맞고, 날짜도 "12월 25일"뿐 아니라 "크리스마스"로 나온다.

### 실습 — LLM 심사 설정

| 심사 지시문의 변수 | 연결할 데이터 |
| --- | --- |
| `{{input}}` | Input (항목의 메시지와 고정한 도구 결과) |
| `{{output}}` | Output (실험에서 만든 답) |
| `{{ground_truth}}` | Expected Output (항목의 통과 조건) |

API 로 확인한 최종 설정:

```
name              holiday-reply-judge
modelConfig       {"provider": "openai", "model": "gpt-4o"}
outputDefinition  dataType: BOOLEAN
variableMapping   input → input, output → output, ground_truth → expected_output
status            active
rule              experimentDatasetId: cmw04kg1u01skad0eeiwipg1i (= holiday-reply)
```

**답을 만드는 모델보다 한 단계 큰 모델**을 쓴다(`gpt-4o-mini` → `gpt-4o`). 같은 모델로 심사하면 자기가 만든 답과 비슷한 실수를 너그럽게 넘긴다.

지시문에서 눈여겨볼 둘:

- **세 번째 예시는 일부러 넣은 경계 사례다.** 12월 25일은 실제로 공휴일이지만 도구 결과에 없으면 실패로 판정하라는 것. 섹션 2 에서 실제로 본 답이고, 안 적으면 심사가 "사실이니 통과"로 넘긴다.
- **`말투, 길이, 이모지, 친절함은 판정하지 않는다`** — LLM 심사는 길고 자신 있게 쓴 답을 후하게 판정한다. 판정하지 않을 것을 함께 적어야 기준 하나로만 본다.

### 문제점과 해결

**(1) `get_prompt()` 의 기본 라벨이 `production` 이다.**

```
404  Prompt not found: 'holiday-reply-answer' with label 'production'
```

`latest` 로 올려 놓고 라벨 없이 부르면 404 다. 라벨을 명시해 해결.

**(2) 점수 조회 API 가 `v2` 에서 410 이다.**

```
HTTP 410  Removed on 2026-11-16. Use GET /api/public/v3/scores instead.
```

v1·v2 엔드포인트 상당수가 **2026-11-16 에 사라진다.** 점수는 `/api/public/v3/scores` 를 쓴다. 보내는 쪽(SDK)은 영향 없고 읽는 API 만 해당한다.

**(3) 조회 API 의 목록 응답이 본문을 안 담는다.** 어제부터 세 번 걸렸다.

`model`, `usage`, `timeToFirstToken`, `traceId`, `comment`, `input`, `output` 이 `null` 로 온다. **값이 없는 게 아니라 목록에 안 담는 것**이다. 확인하려면 집계 API(`/api/public/v2/metrics`)나 화면을 봐야 한다. 실험 항목은 `fields='core,io,scores'` 를 주면 입력·답·점수까지 온다.

**(4) 평가자 화면(v4.72.0)이 교안과 다르다.**

| 걸린 것 | 해결 |
| --- | --- |
| `{{ground_truth}}` 가 기본값 `Input` 으로 걸려 있었다 | 연필 아이콘으로 `Expected Output` 으로 바꿈. **그대로 두면 심사가 통과 조건 대신 질문을 두 번 받아 판정 기준 없이 판정한다** |
| Score description 을 이름 칸으로 착각 | 이름은 3단계 `Name evaluator` 에 있다. 그 이름이 **점수 이름으로도** 쓰인다 |
| 미리보기 `0 matches` | 정상. 그 패널은 이미 돌린 실험에서 샘플을 찾는데 아직 실험이 없다. 교안의 "미리보기로 확인하고 저장"은 실험 기록이 있는 상태를 가정한 것 |
| 내가 준 파일의 `=== System 메시지 ===` 구분선이 지시문에 섞임 | 지우고 다시 넣음. 구분선이라고 표시했어야 했다 |

저장 뒤 규칙(rule) 창에서 `Run evaluator on past observations` 는 **꺼 둔다** — 지난 트레이스까지 심사해 비용만 나간다.

**(5) 판단 이유를 조회 API 로 못 읽는다.** 점수의 `comment` 가 응답에 없다. Tracing 에서 `environment` 를 `langfuse-llm-as-a-judge` 로 걸러 화면에서 읽어야 한다.

### 미룬 것 — 심사 다듬기

심사도 평가 대상이다. 느슨한 심사는 **실패를 통과로 놓쳐서**, 지시문이 나빠져도 점수가 그대로다. 쓸 수 있는 기준은 일치율 90% 이상, 놓친 실패 거의 없음.

1. **사람 라벨과 일치율** — 두 실행의 답 24개에 심사 판정을 보기 전에 직접 통과/실패를 붙여 비교한다. 단, H01·H02·H06·H08·H12 의 판정은 이미 봤으므로 **그 다섯은 오염됐다.** 깨끗한 7항목(H03, H04, H05, H07, H09, H10, H11)의 14개만 쓰거나 일치율을 두 벌로 낸다.
2. **기준 문장을 줄인 심사와 비교** — 예시 세 줄을 뺀 심사를 하나 더 만들어 같은 실행에 건다.
3. **경계 사례** — 지금 지시문에는 금요일·월요일만 있다.

| 경우 | 정할 것 |
| --- | --- |
| 공휴일이 **목요일** (금요일 휴가 내면 나흘) | "금요일 쉬면 나흘"을 제안해야 통과인가 |
| 공휴일이 **토요일** (주말과 겹쳐 쉬는 날이 안 늘어남) | 대체공휴일을 말해야 통과인가 |

## 섹션 4 — 프롬프트 관리와 실험

**한 일** `router` 지시문을 Langfuse 로 옮기고 버전 넷을 비교한 뒤, 지시문으로 안 되는 것을 코드로 옮겼다.
**결과** **T26 이 5/5 실패에서 0/5.** 프롬프트 v2·v3·v4 는 모두 다른 도구에 회귀를 냈다. `production` 라벨은 버전 1 그대로.

### 실습 — 프롬프트를 코드 밖으로

| 항목 | 값 |
| --- | --- |
| 이름 | `router` |
| 변수 | `{{tools}}` 하나 |
| 버전 1 | 지금 코드의 문장 |
| 버전 2 | 기간 규칙 + 전날 규칙 |
| 버전 3 | v2 의 전날 규칙을 다듬음 (중복 금지 문장 추가) |
| 버전 4 | v1 + 기간 규칙만 |

바꾼 파일:

- `app/tracing.py` — `prompt(name, label=None)`. `ENV` 가 `production` 이면 `production` 라벨, 아니면 `staging` 라벨. 못 가져오면 `None`
- `app/router.py` — `tool_lines()`, `router_prompt(tools=None)`, `load_prompt(label=None)` 분리. `choose()` 가 가져온 프롬프트를 `choose-tools` generation 에 연결
- `scripts/upload_router_prompt.py`, `scripts/eval_tools.py --label`

**손으로 옮겨 적지 않았다.** 업로드 스크립트가 코드의 함수를 그대로 부른다.

```python
text = router_prompt("{{tools}}")
```

가져온 문장이 코드와 글자까지 같은 것을 확인했다. 베껴 적으면 실험 결과가 달랐을 때 지시문 탓인지 옮겨 적은 탓인지 가릴 수 없다.

코드 기본 문장으로 돌아갔나: True

### 결과 — 버전 비교

도구 선택은 `[지금]` 과 `[달력]` 을 채우고 도구 목록을 넣는 서비스 코드(`model_choose`)를 거쳐야 해서 화면 실험으로 못 돌린다. `scripts/run_tool_experiments.py` 로 SDK 의 `run_experiment` 에 작업과 코드 평가자를 넘겼다.

v1  args 34, 35          v2  args 34, 32          v3  args 30, 28
v1  args 39, 37, 38      v4  args 37, 37, 35          (코드 수정 뒤, 세 번씩)
```

다섯 번씩 돌린 항목별 실패 수:

| 항목 | v1 실패 | v4 실패 | |

```
v1   get_weather(제주, 10-14)                               정답
v4   get_weather(제주, 10-14) + get_weather(제주, 10-15)     T15
v4   get_air_quality(대구, 10-13) + get_weather(...)        T22
```

기간 규칙은 `get_holidays` 이야기만 하는데 **다른 도구에까지 호출을 덧붙인다.** v2, v3, v4 세 버전 모두 같은 모양이었다.

v3 에서는 금지 문장이 **듣지 않았고 새 중복까지 만들었다.**

```

T26  v2-1  get_holidays({})                                깔끔

### 프롬프트로 고칠 것과 코드로 고칠 것

| 실패 | 고칠 곳 | 바꾸는 구조 | 했나 |
| --- | --- | --- | --- |
| 다음 공휴일을 못 찾음 | 코드 | 기간을 말하지 않으면 인자를 비운다 | **함** (5/5 → 0/5) |
| 시험 전날이 아닌 날로 저장 | 코드 | 모델은 표현을, 코드가 날짜 계산 | **함** (여섯 번 중 한 번 → 전부) |
| 금요일 크리스마스를 연휴가 아니라고 함 | 공휴일 도구 코드 | 도구가 앞뒤 주말을 이어 "25일(금)~27일(일) 사흘 연휴"까지 계산 | **안 함** |

남은 두 줄은 `app/tools.py` 의 `get_holidays` 를 고치는 일이다. **고친 뒤에는 `holiday_reply.jsonl` 의 고정 도구 결과도 새 도구가 내는 문장으로 바꿔야 한다.** 데이터셋 입력이 실제와 달라지면 실험이 의미를 잃는다.

### 문제점과 해결

**(1) 실행 이름을 두 번 재사용했다.** 소량 시험(`--limit 5`)을 `router-staging-v2-1` 이라는 같은 이름으로 돌려 그 실행에 항목이 46개 들어갔다(41+5). 두 번째 배치에서도 같은 이름을 다시 써 앞 배치와 섞였다. 항목별 비교를 시각으로 걸러 겨우 가렸다.

```python
run_name = f"router-{label}-v{version}-{n} {stamp}"     # 시각을 붙여 막았다
```

**(2) `experiments.list_items` 의 `limit` 최대가 100 이다.** 164개를 한 번에 못 받는다. `experiment_name` 으로 실행마다 따로 받았다. 또 기본 응답이 슬림해서 `fields='core,io,scores'` 를 줘야 입력·답·점수가 온다.

**(3) `metrics` 의 `traceId` 는 고카디널리티 차원이다.**

```
High cardinality dimension(s) 'traceId' require both 'config.row_limit' and 'orderBy' with direction 'desc' on a measure field.
```

**(4) `MAX_TOOLS` 가 f-string 으로 박혀 있다.** Langfuse 문장에는 `최대 2개` 로 리터럴이 됐다. 코드에서 바꿔도 프롬프트는 안 따라간다. 실제 개수 제한은 `choose()` 의 `result.tools[:MAX_TOOLS]` 가 걸어 동작은 안 깨진다.

## 섹션 5 — A/B 테스트

**한 일** 표본 수를 계산해 쓸 수 있는지 따지고, 분배만 구현해 검증했다.
**결과** 분배는 동작(480/520). **이 트래픽으로는 판단에 못 쓴다** — 78~156일 필요.

### 실습 — 쓸 수 있는지부터 계산

좋아요 비율을 50% → 60% 로 올렸는지 보려면(α=0.05, 검정력 80%) 그룹당 약 390개, 합 780개의 **반응**이 필요하다. 버튼을 누르는 사람은 일부(5~10%)이므로 메시지로는 7,800~15,600개다.

| 트래픽 | 반응률 10% | 반응률 5% |
| --- | --- | --- |
| 하루 100개 (교안 시나리오) | 78일 | 156일 |
| 하루 12개 (이 서비스의 실제) | 650일 | 1,300일 |

이틀간 `staging` 의 `chat-turn` 은 24개였고 그마저 시험한 것이다. `user-feedback` 점수는 최근 100개 중 0개다.

**지시문 한 줄 고치는 데 두 달을 기다릴 수 없다.** 오늘 `tool-selection` 41개를 다섯 번씩 돌려 **5분 만에** v4 가 T15·T22 를 망친다는 걸 알았다. A/B 였다면 두 달 뒤에 알았거나 아예 몰랐다.

A/B 가 필요한 자리는 따로 있다 — 데이터셋으로 못 재는 것, 즉 "사용자가 짧은 답을 더 좋아하는가" 같은 취향 문제다. 정답이 없어 평가자로 못 가린다. 다만 그것도 트래픽이 있어야 한다.

### 실습 — 분배 구현

새 버전이 **크게 나빠지지 않았는지 지켜보는 용도**로는 쓸 수 있다.

```python
def ab_variant(uid):
    bucket = int(hashlib.sha256(str(uid).encode("utf-8")).hexdigest(), 16) % 100
    return "a" if bucket < AB_SPLIT else "b"      # AB_SPLIT = 50
```

- 환경변수 `AB_TEST=on` 일 때만 동작한다. 꺼져 있으면 평소대로 `ENV` 에 맞는 라벨을 쓴다.
- **요청마다 무작위로 고르지 않는다.** 그러면 한 사용자의 대화 안에서 말투가 오락가락하고, 한 사람의 피드백이 두 버전에 섞여 비교를 망친다.
- `prod-a` / `prod-b` 를 가져오지 못하면 평소 라벨로 돌아간다.
- 트레이스 metadata 에 `ab_variant` 를 남겨 Tracing 화면에서 그룹별로 거를 수 있다.

### 결과

```
1000명 분배        {'a': 480, 'b': 520}
같은 ID 다섯 번     ['b', 'b', 'b', 'b', 'b']
AB_TEST=off        라벨 None (평소 경로)
실제 모델 두 턴     ab-user-1 → 그룹 b → 프롬프트 버전 4
                   ab-user-2 → 그룹 a → 프롬프트 버전 1
트레이스           버전 4 한 개, 버전 1 한 개
```

확인 뒤 `AB_TEST` 를 끄고 `prod-a`, `prod-b` 라벨을 뗐다.

### 문제점과 해결

**가짜 LLM 은 프롬프트 경로를 타지 않는다.** `can_reason=False` 라 규칙으로 고른다. 처음에 fake 로 돌렸더니 트레이스에 프롬프트 버전이 비어 있었다. **A/B 확인은 실제 모델로 해야 한다.**

### 기타 — 승자 정하기에서 지킬 것

- 내보낼 기준(모을 수, 지표, 유의수준, 의미 있다고 볼 최소 차이)을 **시작 전에** 적는다.
- 통계적으로 유의해도 차이가 0.5%p 면 바꿀 이유가 약하다. 비용과 지연 시간도 함께 본다.
- **매일 들여다보다 p값이 처음 0.05 아래로 내려간 날 멈추지 않는다.** 여러 번 볼수록 우연한 차이를 승자로 고를 확률이 커진다. 정한 수를 다 모은 뒤 한 번 판정한다.

### 실습 — CI 평가 게이트

평가는 만들어 두기만 하면 쓰이지 않는다. **확인할 방법이 없어서가 아니라 확인하지 않고 내보낼 수 있어서** 같은 실패가 반복된다.

`.github/workflows/eval.yml`

- **PR 마다 자동으로 돌지 않는다.** 실제 LLM 을 41번 부른다. PR 에 `eval` 라벨을 붙였을 때나 Actions 의 Run workflow 를 눌렀을 때만 돈다.

- Langfuse 키는 넣지 않는다. 키가 없으면 계측이 꺼지고 **코드의 기본 프롬프트**로 평가한다. 코드 변경을 재는 게이트이므로 배포된 프롬프트가 아니라 코드의 문장이 맞다.
- 액션 버전은 `ci.yml` 과 같은 `actions/checkout@v7`, `actions/setup-python@v7`.

| 지점 | 돌릴 평가 | 멈추는 조건 | 이 서비스에서 |

요청이 하루 수십 건인 이 서비스에서는 **배포 전 실험의 비중이 크고**, 트래픽을 나눠 보는 단계는 보조 수단이다.

### 가드레일 현황

가드레일은 모델의 판단과 상관없이 **코드로** 막는 규칙이다.

| 대상 | 지금 | 위치 |
| --- | --- | --- |
| 위기 표현 | **코드** | `app/safety.py` `is_crisis` |
| 민감 정보 기억 저장 | **코드** | `app/safety.py` `is_sensitive` |
| Langfuse 로 보낼 원문 | **코드** | `app/tracing.py` `mask` (전화번호·이메일·카드·주민번호) |
| 프롬프트 인젝션 (`safety.jsonl` 5개) | **AI 판단만** | 없음 |
| 지시문 공개 거절 (`docs/examples.md` E20) | **AI 판단만** | 없음 |

인젝션과 지시문 공개는 **지시문에 규칙을 더하는 것만으로는 막을 수 없다.** 오늘 router 에서 본 것처럼 규칙을 적어도 모델이 안 지키는 일이 있다.

다음에 넣을 것: 답에 고정 규칙 문장이 그대로 나오면 내보내지 않는 검사. 다만 답을 스트리밍으로 보내므로 **모아 두었다가 검사하면 첫 글자가 늦어진다.** 쌓이는 답을 보며 표시가 나타나면 스트리밍을 끊고 거절 문구로 바꾸는 쪽이 맞다.

### 기타 — 개인정보

Langfuse 무료 플랜은 30일 동안 데이터를 보관한다. 사용자가 대화에 쓴 전화번호나 카드 번호도 그동안 남는다. 어제 마스킹을 넣어 그 네 가지는 가려서 보낸다. **트레이스를 보는 사람이 모든 사용자의 대화를 볼 수 있다는 점**은 운영자가 정할 일이다.

### 오늘 이 서비스로 채운 예

```
서비스: AI 친구 에이전트
고칠 실패 유형: 도구 인자의 날짜와 기간이 틀림   처음 어긋난 단계: 도구 선택
판정 기준 문장: 기간을 말하지 않은 공휴일 질문은 다음 공휴일이 들어가는 기간을 조회하고,
               "X 전날"은 X의 하루 앞 날짜로 저장한다
데이터셋 이름: tool-selection                    항목 수: 실패 8 / 정상 33
고정해 넣을 앞 단계 결과: 없음 (도구 선택이 첫 모델 호출)
평가자: 코드                 판정할 것: 고른 도구 이름과 인자, 기간이 다음 공휴일을 품는가
고칠 곳: 코드                이유: 날짜를 더하고 빼는 계산이라 매번 같은 답이 나와야 한다
회귀 확인 데이터셋: tool-selection 41개 전체
내보낼 기준: 고친 유형 통과 2개 이상 증가, 전체 통과 감소 2개 이하
평가를 걸 지점: 머지 전 (eval 라벨)
```

`holiday-reply` 쪽은 **앞 단계 결과를 고정해 넣은 예**다. 답이 틀린 원인이 도구 결과에 따라 흔들려서, 도구 결과를 문장으로 박아 두고 답만 판정했다.

### 계획을 세울 때 걸리는 자리

- **실패한 단계의 입력과 출력이 트레이스에 없으면 데이터셋보다 계측을 먼저 고친다.** 트레이스에서 실패를 읽을 수 없으면 항목도 만들 수 없다.
- 판단이 서지 않으면 프롬프트 버전을 **먼저 두 번** 실험하고, 같은 항목이 같은 답으로 계속 틀리면 코드로 옮긴다. 오늘 T34 가 그랬다 — 여섯 번 중 한 번만 맞았고 틀릴 때는 늘 같은 날짜였다.
- 내보낼 기준은 **실험 전에** 숫자로 적는다. 결과를 본 뒤 정하면 조금이라도 오른 쪽을 내보내게 된다.
