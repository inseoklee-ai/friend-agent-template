# Langfuse 로 에이전트 품질 지키기

2026-11-03 학습 정리. 어제(2026-11-02) 붙인 계측 위에서 평가를 올린다.
어제 기록은 `docs/langfuse-plan.md` 와 실습 기록 아티팩트에 있다.

## 오늘의 목표

1. 실패 트레이스에서 처음 어긋난 단계를 찾아 **실패 유형**과 **판정 기준 문장**을 만든다
2. 놓친 실패를 담은 **데이터셋**을 만들고, 코드 채점과 LLM 심사 중 알맞은 평가자를 고른다
3. Langfuse 에서 **LLM 심사**를 설정해 실험 결과를 판정하고, 판정 이유를 읽어 기준대로 판정했는지 확인한다
4. 프롬프트를 **Langfuse 프롬프트 관리**로 옮기고, 버전과 라벨로 배포하고 롤백한다
5. 프롬프트 두 버전을 같은 데이터셋과 평가자로 **실험**해 비교하고, 프롬프트로 고칠 실패와 코드로 고칠 실패를 가른다
6. **프롬프트 A/B 테스트**를 설계하고, 트래픽으로 표본 수와 기간을 따져 쓸지 말지 정한다

### 계측된 관찰 단위

| 단계 | 이름 | 종류 |
| --- | --- | --- |
| 한 턴 전체 | `chat-turn` | 트레이스 |
| 안전장치 | `safety` | span |
| 도구 선택 | `choose-tools` | generation |
| 도구 실행 | `tool:<도구 이름>` | span |
| 답 만들기 | `reply` | generation |

## 평가자 고르는 기준

| | 코드 채점 | LLM 심사 |
| --- | --- | --- |
| 쓸 때 | 정답이 정해짐 — 고른 도구 이름, 인자, 포함해야 할 문자열, 안전 응답 여부 | 정답이 하나로 안 정해짐 — 말투, 위로가 되는지, 도구 실패를 어떻게 말했는지 |
| 장점 | 빠르고 공짜. 같은 입력에 같은 판정 | 사람이 읽어야 알 수 있는 것을 판정 |
| 단점 | 표현이 달라지면 틀렸다고 함 | 비용이 들고, 심사도 비결정론이라 판정 이유를 읽어 봐야 함 |

어제 본 2번·3번 실패는 **고른 도구 이름으로 판정된다** → 코드 채점이 맞다.
"도구가 실패했을 때 어떻게 말했는지"는 → LLM 심사가 맞다.

### 섹션 1 — 시작 상태 (2026-11-03)

| 필요한 상태 | 결과 |
| --- | --- |
| 로컬 실행 | `python -c "import app.main"` ok. provider=openai, model=gpt-4o-mini |
| 실제 LLM 키 | `LLM_PROVIDER=openai` — fake 아님 |
| Langfuse 키 | `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL` 모두 있음 |
| 단계별 계측 | 어제 완료. `chat-turn` 아래 `safety`, `choose-tools`, `tool:*`, `reply`, `memory-update` |
| 트레이스 30개 이상 | **154개** (기준 충족) |

교안이 요구하는 "도구 선택의 인자"와 "도구 실행의 결과"가 둘 다 남아 있다. 어제 `choose-tools` 에 고른 도구·인자·확신도·`decided_by` 를, `tool:<이름>` 에 인자·결과 요약·`ok` 를 남겼다.

환경별 트레이스 수는 아래와 같다.

| environment | chat-turn | 비고 |
| --- | --- | --- |
| `default` | 49 | 중첩이 깨져 있던 때. `environment` 를 붙이기 전이라 기본값으로 들어갔고, 부모를 잃은 자식들도 루트로 섞여 있다 |
| `local` | 23 | 속성을 붙인 뒤의 로컬 |
| `staging` | 24 | staging |
| `repro`, `score-test` | 8 | 어제 재현·점수 시험용 |

`default` 49개는 **섞어 쓰면 안 된다.** 오늘 실패를 셀 때는 `environment` 로 `local` 과 `staging` 만 골라야 한다.

### 트레이스 모으기

`scripts/send_eval_messages.py` 를 만들어 `data/eval/` 의 메시지 56개를 로컬 서버로 보냈다.

```
보냄 56 / 실패 0
한 턴 $0.000336 (3건으로 먼저 재고 전체를 보냄)
```

`.env` 가 `AUTH=supabase` 라서 토큰 없이 `/api/chat` 을 치면 401 이다. 서버를 로그인 없이 띄워야 한다.

```
$env:AUTH="none"; $env:STORAGE="memory"; uvicorn app.main:app --port 8080
```

`STORAGE=supabase` 는 `AUTH=supabase` 와만 쓸 수 있어서 저장소도 메모리로 바꾼다. 스크립트는 401 을 만나면 그 줄을 찍고 바로 멈춘다. 56건을 다 날리지 않기 위해서다.

### 섹션 2 — 네 대화의 트레이스 읽기 (2026-11-03 화요일 기준)

날짜 관련 세 대화를 세 번씩, 턴마다 대화를 지우고 보냈다. 답이 실행마다 달라지기 때문이다.

**"다음 공휴일 언제야?" — 처음 어긋난 단계: 도구 선택의 인자**

도구 선택이 3번 모두 `from 2026-11-03, to 2026-11-30` 으로 **이번 달까지만** 잡았다. 다음 공휴일인 12월 25일이 기간 밖이다. 도구는 "공휴일이 없습니다"라고 **맞게** 답했다. 그런데 답은 셋 다 달랐다.

| 실행 | 답 | 문제 |
| --- | --- | --- |
| 1 | "다음 공휴일은 11월 15일 수능날" | 도구 결과에 없는 날짜. 수능은 공휴일도 아니다 |
| 2 | "2026년 이후로는 나와 있지 않아" | 조회하지도 않은 기간을 단정 |
| 3 | "다음 공휴일은 12월 25일 크리스마스" | **답은 맞지만** 도구 결과에 없는 정보다. 모델이 알고 있어 운 좋게 맞았다 |

3번이 중요하다. 답이 맞았다고 단계가 맞은 것이 아니다.

**"12월에 연휴 있어?" — 처음 어긋난 단계: 도구 선택(중복) + 답 만들기(연휴 판정)**

`get_holidays` 를 3번 모두 **두 번씩** 불렀다. 실행 1은 12월과 11월(불필요), 실행 2·3은 12월을 두 번(완전 중복). 답은 틀리지 않지만 외부 API 시간과 토큰이 그만큼 더 든다. 어제 `get_air_quality` 에서 본 것과 같은 실패다.

도구는 `12월 25일(금) 크리스마스` 를 맞게 돌려줬다. 금요일 공휴일이면 주말과 이어져 사흘을 쉰다. 그런데 답은 이렇게 갈렸다.

| 실행 | 답 | 판정 |
| --- | --- | --- |
| 1 | "크리스마스인 25일(금)이 공휴일이야" | 연휴를 물었는데 답하지 않음 |
| 2 | "25일이 금요일이라서 연휴 느낌 낼 수 있을 거야! 다른 연휴는 없고" | 애매 |
| 3 | "연휴는 없지만" | **틀림** |

도구가 요일까지 줬으므로 연휴 여부는 **답 만들기**가 따질 몫이다.

**"금요일 시험 전날 밤에 일찍 자라고 알려 줘" — 처음 어긋난 단계: 도구 선택의 인자**

금요일은 11월 6일이고 전날은 11월 5일(목)이다.

| 실행 | `due_at` | 판정 |
| --- | --- | --- |
| 1 | `2026-11-05T21:00` (목) | 맞음 |
| 2 | `2026-11-05T21:00` (목) | 맞음 |
| 3 | `2026-11-06T21:00` (금) | **틀림** — 전날이 아니라 당일 |

3번은 답도 "금요일 밤 9시"라고 해서 일관되게 틀렸다. 답만 보면 그럴듯해 트레이스 없이는 못 잡는다.

### 실패 유형표

9턴에서 나온 것을 묶었다. 개수는 9턴 기준이라 적다.

우선순위는 개수만으로 정하지 않는다. 2번은 사용자가 그대로 믿고 움직일 수 있어 피해가 크다. 4번은 답을 틀리게 하지 않지만 비용과 지연에 바로 나타난다.

| 8 | 상대 날짜와 시각 표현을 잘못 계산 | 2/41 | "모레"는 오늘 +2일, "아침"은 08:00 으로 잡는다 | 코드 |

유형 4(중복·불필요한 도구)와 유형 5("X 전날")가 여기서도 나왔다. 날짜 대화 9턴에서 본 것이 41건 평가에서도 재현됐으므로 **우연이 아니다**.

T34 는 날짜 대화에서 본 것과 같은 메시지인데 틀리는 방향이 다르다. 9턴 실습에서는 하루 **뒤**(당일)로, 41건 평가에서는 하루 **앞**으로 갔다. 전날 계산이 한쪽으로 치우친 게 아니라 **불안정한 것**이다.

### 고친 것 — `record_usage` 가 트레이스 밖에서 오류 줄을 찍던 문제

평가를 돌리자 이 줄이 41번 찍혔다.

```
Context error: No active span in current context. Operations that depend on an active span will be skipped.
```

`scripts/eval_tools.py` 는 `app/router.py` 의 `model_choose` 를 직접 불러서 `choose-tools` 관찰 단위 밖에서 돈다. 그런데 `app/llm.py` 가 호출마다 `tracing.record_usage()` 를 부르고, 그 안의 `update_current_generation()` 이 열린 span 을 못 찾아 SDK 가 오류를 찍었다.

`record_usage()` 앞에 열린 span 이 있는지 확인하는 줄을 넣어 막았다. `get_current_trace_id()` 로 확인하면 같은 오류 줄이 또 찍히므로, OpenTelemetry 의 span context 로 조용히 본다.

```python
def _in_span():
    from opentelemetry import trace as otel_trace
    return otel_trace.get_current_span().get_span_context().is_valid
```

기록이 필요한 자리(트레이스 안)에서는 그대로 동작하고, 트레이스 밖에서는 조용히 건너뛴다. 섹션 3 에서 데이터셋을 돌릴 때도 같은 자리를 지나므로 미리 고쳐 둔다. `pytest` 12개 통과.

## 섹션 3 — 고치기 전에 잴 방법부터

고친 뒤에 무엇을 보고 "고쳐졌다"고 말할지부터 정한다. LLM 은 같은 메시지에도 실행마다 답이 달라서, 대화창에서 두세 번 맞았다고 고쳐진 것이 아니다. 다른 메시지가 나빠졌는지도 대화 몇 개로는 모른다.

### 같은 평가를 두 번 돌린 결과

```
1회차   도구 정답 39/41,  도구와 인자 모두 정답 36/41
2회차   도구 정답 39/41,  도구와 인자 모두 정답 35/41
```

맞힌 수만 보면 한 개 차이지만, **틀린 항목의 구성이 다르다**.

| 항목 | 1회차 | 2회차 | 내용 |
| --- | --- | --- | --- |
| T16 `지금 밖에 추워?` | 실패 | 실패 | 도구를 안 고름 |
| T19 `그럼 모레는?` | 실패 | 실패 | 모레를 하루 앞으로 |
| T33 `다음 주 월요일 아침` | 실패 | 실패 | 08:00 을 09:00 으로 |
| T38 `알림 취소해 줘` | 실패 | 실패 | `list_reminders` 를 덧붙임 |
| T34 `금요일 시험 전날` | 실패 | **통과** | 전날 계산이 실행마다 갈림 |
| T15 `모레 제주 여행` | 통과 | **실패** | |
| T22 `내일 대구 초미세먼지` | 통과 | **실패** | |

**늘 틀리는 것은 4개**(T16, T19, T33, T38)이고, 나머지 3개는 실행마다 갈린다. 섹션 4 에서 두 지시문을 비교할 때 **한 번씩 돌린 한두 개 차이로는 어느 쪽이 낫다고 말할 수 없다**는 뜻이다. T34 는 어제 유형 5 로 올린 "X 전날" 실패인데, 2회차에서는 통과했다.

### 지금 평가가 잡는 것과 못 잡는 것

| 실패 | 지금 평가에서 | 이유 |
| --- | --- | --- |
| 시험 전날이 아닌 날로 저장 | **잡힘** | T34 에 `expected_args` 로 `due_at: 2026-10-15T21:00` 이 적혀 있다 |
| 다음 공휴일을 못 찾음 | 안 잡힘 | T26 은 `expected_args` 가 `{}` 라서 `get_holidays` 를 고르기만 하면 통과한다 |
| 도구 결과에 없는 날짜를 말함 | 안 잡힘 | 답에서 생기는 실패인데, 이 평가는 도구 선택까지만 본다 |
| 연휴를 잘못 말함 | 안 잡힘 | 이것도 답에서 생기는 실패다 |

T26 의 실제 내용은 이렇다.

```json
{"id": "T26", "message": "다음 공휴일 언제야?", "expected_tools": ["get_holidays"], "expected_args": {}}
```

**평가는 정답에 적어 둔 것만 채점한다.** 적어 두지 않은 기간은 틀려도 통과하고, 보지 않는 단계(답 만들기)는 아예 범위 밖이다. 어제 트레이스에서 본 "기간이 이번 달로 좁아 12월 25일이 빠진" 실패가 이 평가를 그대로 통과한다.

### 다음 공휴일 실패를 잡게 하기 — T26 고치기

기간을 기대 결과에 **그대로 적으면 안 된다.** 인자를 비워 도구가 1년을 찾게 하는 것도 올바른 방법이라, 맞는 답까지 틀렸다고 세기 때문이다. 확인할 것은 "그 기간 안에 다음 공휴일이 들어가는가" 하나다.

그래서 기대 결과에 **다음 공휴일 날짜**를 적고, 모델이 준 기간이 그 날짜를 품는지 코드로 판정한다.

```json
{"id": "T26", "message": "다음 공휴일 언제야?", "expected_tools": ["get_holidays"],
 "expected_args": {}, "expected_covers": {"get_holidays": "2026-12-25"}}
```

`scripts/eval_tools.py` 에 `covers_match()` 를 더했다. 기간을 비워 두면 통과로 센다.

```python
start, end = str(actual.get("from") or ""), str(actual.get("to") or "")
if not start and not end:
    return []                      # 비워 두면 도구가 1년을 찾는다
if (start or "0000-01-01") <= want <= (end or "9999-12-31"):
    return []
```

돌려 보니 바로 잡혔다.

```
T26 다음 공휴일 언제야?  →  기간에 2026-12-25 가 빠짐: from 2026-10-12, to 2026-10-31
```

3회차 결과는 `도구 정답 39/41, 도구와 인자 모두 정답 34/41` 이다. T26 이 실패로 세어지면서 하나 줄었다. 1·2회차와 바로 비교할 수 없는 숫자다.

세 번 돌린 것을 모으면 **늘 틀리는 것은 T16, T33, T38 셋뿐**이다. T19, T22, T34, T15, T28 은 실행마다 갈린다. 3회차에서 T22 는 날짜가 아니라 **지역**을 틀렸고(`대구` → `서울`), T28 은 12월을 물었는데 **10월**을 조회했다.

### holiday-reply 데이터셋

답에서 생기는 실패(유형 2·3)는 메시지를 처음부터 실행하면 못 가린다. 도구 선택이 고른 기간에 따라 도구 결과가 매번 달라져, 답이 틀렸을 때 **답 지시문 탓인지 도구 결과 탓인지** 알 수 없기 때문이다.

그래서 `data/eval/holiday_reply.jsonl` 에는 **도구 결과를 문장으로 고정해** 넣고 답만 만들게 한다. 12개를 넣었다(실패 사례 7, 정상 사례 5).

| id | 메시지 | 고정한 도구 결과 | 통과 조건 | 종류 |
| --- | --- | --- | --- | --- |
| H01 | 다음 공휴일 언제야? | 11월에 공휴일 없음 | 결과에 없는 날짜를 공휴일이라고 말하지 않는다 | 실패 |
| H02 | 12월에 연휴 있어? | 12월 25일(금) 크리스마스 | 25일부터 27일까지 사흘을 쉰다고 말한다 | 실패 |

### 평가자 고르기

출력 하나를 보고 통과와 실패를 판정하는 것이 **평가자(evaluator)** 다.

| 실패 | 데이터셋 | 판정할 것 | 평가자 |
| --- | --- | --- | --- |
| 시험 전날이 아닌 날로 저장 | tool-selection | `due_at` 이 정답 시각과 같은가 | 코드 (이미 있음) |
| 다음 공휴일을 못 찾음 | tool-selection 의 T26 | 기간에 다음 공휴일이 들어가는가 | 코드 (오늘 더함) |
| 없는 공휴일을 말함 | holiday-reply | 답에 나온 날짜가 모두 도구 결과에 있는가 | LLM 심사 |
| 연휴를 잘못 말함 | holiday-reply | 주말과 이어져 사흘 쉰다고 말했는가 | LLM 심사 |

답에서 생기는 두 실패를 LLM 심사에 맡기는 이유는 **맞는 표현이 여러 가지**이기 때문이다. 연휴는 "사흘 쉴 수 있어", "주말까지 쭉 쉬네"로 다 맞고, 날짜도 "12월 25일"뿐 아니라 "크리스마스"로 나온다. 코드로 다 뽑아 비교하기 어렵다.

판정은 점수가 아니라 **통과/실패 두 가지**로 받는다. 7점과 8점의 차이는 사람도 설명하기 어렵지만, 통과와 실패로 받으면 실패한 항목만 열어 바로 읽을 수 있다.

다시 실행해도 수가 그대로다. 항목 id 를 `<데이터셋>-<항목 id>` 로 고정해 보내서 새로 만들지 않고 덮어쓴다.

- `holiday-reply` 항목의 `input` 에 `message` 와 `tool_result` 가 함께 있음

### 답 지시문을 Langfuse 에 두기

Langfuse 화면의 실험은 **Langfuse 에 저장된 프롬프트** 하나에 데이터셋 항목의 input 을 넣고 모델을 부른다. 그래서 답을 만들 지시문이 먼저 Langfuse 에 있어야 한다.

교안의 예시 문장을 손으로 옮기지 않고 `scripts/upload_reply_prompt.py` 가 **`app/agent.py` 의 `system_prompt` 를 그대로 불러** 만든다. 옮겨 적으면 서비스와 어긋나고, 답이 틀렸을 때 지시문 탓인지 옮겨 적은 탓인지 가릴 수 없다.

```python
system = system_prompt(DEFAULT_CHARACTER, NOW, "서울", [], None, ["{{tool_result}}"])
return [{"role": "system", "content": system}, {"role": "user", "content": "{{message}}"}]
```

`NOW` 는 `2026-11-02(월) 14:00 Asia/Seoul` 이다. 데이터셋의 고정 도구 결과와 **같은 날**로 둬야 "이번 주", "다음 공휴일"이 가리키는 날짜가 맞는다. 어긋나면 답이 틀렸을 때 지시문 탓인지 날짜 탓인지 가릴 수 없다.

올린 결과를 확인했다.

```
holiday-reply-answer  버전 1 | 라벨 ['latest'] | 변수 ['message', 'tool_result']
[지금] 11월 2일(월) 14:00 (Asia/Seoul), 사용자 지역: 서울
```

변수 이름은 데이터셋 항목 `input` 의 키와 **같아야** 값이 채워진다.

`get_prompt()` 의 기본 라벨은 `production` 이라, 라벨 없이 부르면 `404 Prompt not found ... with label 'production'` 이 난다. 섹션 4 에서 라벨로 배포할 때 다시 나올 자리다.

### LLM 심사 설정

Langfuse 의 LLM 심사는 네 가지를 정하면 돈다 — **판정할 모델**, **심사 지시문**, **판정 결과의 형식**, **지시문 변수에 넣을 데이터**.

| 심사 지시문의 변수 | 연결할 데이터 | holiday-reply 실험에서 들어가는 값 |
| --- | --- | --- |
| `{{input}}` | Input | 항목의 메시지와 고정한 도구 결과 |
| `{{output}}` | Output | 실험에서 답 지시문으로 만든 답 |
| `{{ground_truth}}` | Expected Output | 항목의 통과 조건 |

심사 모델은 **구조화 출력(structured output)** 을 지원해야 한다. 저장할 때 `Model configuration not valid for evaluation` 이 나오면 그 모델이 지원하지 않거나 연결 설정이 틀린 것이다.

**답을 만드는 모델보다 한 단계 큰 모델**을 고른다. 같은 모델로 심사하면 자기가 만든 답과 비슷한 실수를 너그럽게 넘긴다. 이 서비스의 답 모델이 `gpt-4o-mini` 이므로 심사는 `gpt-4o` 로 둔다.

API 로 확인해 보니 **LLM Connection 이 아직 하나도 없다**. 실험에서 답을 만드는 모델과 심사 모델이 모두 이 연결로 불리므로, 이것부터 등록해야 실험이 돈다.

```python
lf.api.llm_connections.list()   # -> []
```

#### 심사 지시문에서 눈여겨볼 두 가지

지시문의 세 번째 예시는 **일부러** 넣은 경계 사례다.

```
도구 결과: 2026-11-02부터 2026-11-30까지 공휴일이 없습니다.
답: "이번 달엔 공휴일이 없어. 다음은 12월 25일 크리스마스야."
판정: 실패 (12월 25일이 도구 결과에 없다)
```

12월 25일은 **실제로** 공휴일이다. 그래도 서비스가 받은 도구 결과에는 없으므로 근거 없이 지어낸 날짜다. 이런 사례를 적어 두지 않으면 심사는 "사실이니 통과"로 판정한다. 섹션 2 에서 실제로 본 답이기도 하다.

`말투, 길이, 이모지, 친절함은 판정하지 않는다` 도 같은 이유다. LLM 심사는 **길고 자신 있게 쓴 답을 후하게 판정**하는 경향이 있어서, 판정할 것과 판정하지 않을 것을 함께 적어야 기준 하나로만 판정한다.

#### 판정은 Boolean 으로

점수가 아니라 통과/실패로 받는다. 7점과 8점의 차이는 사람도 설명하기 어렵지만, 통과/실패로 받으면 **실패한 항목만 열어 바로 읽을** 수 있다.

### 첫 실험 — 지금 상태 재기

**실험(experiment)** 은 데이터셋의 항목마다 같은 작업을 실행하고 그 결과를 평가자로 판정해 한 번의 실행 기록(run)으로 남기는 것이다. 답 지시문 버전 1 로 돌린 숫자가 섹션 4 에서 고친 뒤 비교할 기준이 된다.

실험은 항목 수만큼 **답 모델**을, 다시 항목 수만큼 **심사 모델**을 부른다. holiday-reply 는 12개이므로 한 번 돌릴 때 24번, 두 번 돌리면 48번이다.

같은 설정으로 **두 번** 돌린다. 섹션 3 에서 본 대로 한 번 돌린 결과로는 어느 쪽이 나은지 말할 수 없기 때문이다.

실패 판정이 나온 항목은 **판단 이유를 꼭 읽는다.**

- 이유가 답의 실제 문제를 짚으면("12월 25일이 도구 결과에 없다", "주말과 이어진다는 말이 없다") 심사가 기준대로 판정한 것이다
- 말투나 길이를 이유로 들면 심사 지시문이 **기준 밖의 것**을 보고 있는 것이다

판정이 안 보이면 Tracing 에서 `environment` 를 `langfuse-llm-as-a-judge` 로 거른다. 심사 한 번이 트레이스 하나로 남는다. `Error` 면 심사 모델 연결을, `Delayed` 면 속도 제한으로 다시 시도 중인지 본다.

이것으로 평가자 고르기 표의 **네 줄 모두** 데이터셋과 평가자가 짝지어졌다. 섹션을 시작할 때는 시험 전날 실패 하나만 잡혔다.

#### 만든 심사 (API 로 확인한 값)

```
name              holiday-reply-judge
modelConfig       {"provider": "openai", "model": "gpt-4o"}
outputDefinition  dataType: BOOLEAN
variableMapping   input → input, output → output, ground_truth → expected_output
status            active
rule              experimentDatasetId: cmw04kg1u01skad0eeiwipg1i (= holiday-reply)
```

화면 작업에서 걸린 것 셋:

1. **`{{ground_truth}}` 가 기본값 `Input` 으로 걸려 있었다.** 그대로 두면 심사가 통과 조건 대신 질문을 두 번 받아, 판정 기준 없이 판정한다. 연필 아이콘으로 `Expected Output` 으로 바꿔야 한다.
2. **Score description 은 이름 칸이 아니다.** 점수가 무슨 뜻인지 적는 칸이고, 이름은 3단계 `Name evaluator` 에 있다. 이 이름이 **점수 이름으로도** 쓰인다.
3. 오른쪽 미리보기의 `0 matches` 는 정상이다. 그 패널은 **이미 돌린 실험**에서 샘플을 찾는데, 아직 실험이 없다. 교안의 "미리보기로 확인하고 저장" 은 실험 기록이 있는 상태를 가정한 것이다. 우리는 이 심사가 첫 실험의 판정자라 순서가 반대다.

v4.72.0 화면은 교안과 구성이 다르다. `New evaluator` 한 화면에서 1) Define evaluation 2) Map variables to data 3) Name evaluator 를 차례로 채우고, 저장 뒤 규칙(rule) 창이 따로 뜬다. 거기서 `Run evaluator on past observations` 는 **꺼 둔다** — 지난 트레이스까지 심사해 비용만 나간다.

### 첫 실험 결과 — reply-v1-1 과 reply-v1-2

같은 설정(프롬프트 v1, `gpt-4o-mini`, 데이터셋 holiday-reply)으로 두 번 돌렸다.

```
reply-v1-1: 통과 9/12
reply-v1-2: 통과 7/12
```

| 항목 | 종류 | v1-1 | v1-2 | |
| --- | --- | --- | --- | --- |
| H01 | 실패 | True | **False** | 갈림 |
| H02 | 실패 | False | False | 늘 실패 |
| H03 | 정상 | True | True | |
| H04 | 정상 | True | True | |
| H05 | 실패 | True | True | 통과 |

| H07 | 정상 | True | True | |

**정상 사례 5개는 두 번 다 통과했다.** 지금 지시문이 멀쩡히 하던 일을 섹션 4 에서 망가뜨리면 여기서 드러난다.

#### 같은 설정인데 2개 차이

이것이 섹션 3 에서 본 것의 실증이다. **프롬프트도 모델도 데이터셋도 같은데 9와 7이 나왔다.** 고친 뒤 한 번 돌려 8이 나왔다고 좋아지거나 나빠졌다고 말할 수 없다.

갈린 두 항목의 답을 보면 이유가 분명하다.

```
H01  v1-1  "다음 공휴일은 2026년 11월부터 30일까지 없어서, 그 이후로는 확인해봐야 해."   → 통과
     v1-2  "이번 달에는 공휴일이 없고, 다음 달 12월 25일이 크리스마스야!"              → 실패

H06  v1-1  "올해는 금, 토, 일 이렇게 3일 연휴로 예상할 수 있을 것 같아!"               → 통과
     v1-2  "그 주에 따라 연휴가 달라질 수 있어. 대체로 주말과 연결되면..."             → 실패
```

H01 의 v1-2 답이 섹션 2 에서 본 **지어내기 실패 그대로**다. 12월 25일은 실제로 공휴일이지만 도구 결과에는 없다. 심사가 이걸 실패로 잡았다 — 심사 지시문의 세 번째 예시가 일한 것이다.

#### 늘 실패하는 세 항목

```
H02  "12월에는 크리스마스가 25일 금요일에 있어. 그 주에 연휴를 계획하면 좋을 것 같아!"
     → 금요일이라고 말했지만 주말과 이어 사흘 쉰다는 말이 없다

H08  "3월에는 3일에 삼일절이 있어! 연휴는 아니지만 공휴일이니까..."
     → 도구 결과는 3월 1일인데 3일이라 했고(지어내기), 연휴가 아니라고 했다. 두 실패가 겹쳤다

H12  "수요일에 공휴일이 있으면 그 전후에 하루 쉴 수 있으면 연휴로 간주할 수 있어!"
     → 도구 결과에 없는 수요일 공휴일을 전제로 답했다. 질문의 틀린 전제에 끌려갔다
```

이 셋이 섹션 4 에서 지시문으로 고칠 과녁이다.

#### 걸린 것 — 판단 이유를 조회 API 로 못 읽는다

점수의 `comment`(판단 이유)가 조회 API 응답에 없다. 어제부터 반복되는 패턴이다.

```python
lf.api.scores.get_many(name='holiday-reply-judge', fields='core')
# -> dataType, value, id, projectId, name, source, timestamp, environment, createdAt, updatedAt
```

`fields` 에 `core,io` 나 `comment` 를 주면 거부된다. 실험 항목 쪽은 `fields='core,io,scores'` 로 입력·답·점수까지 받을 수 있지만 거기서도 `comment` 는 비어 있다.

**판단 이유는 화면에서 읽어야 한다.** Tracing 에서 `environment` 를 `langfuse-llm-as-a-judge` 로 거르면 심사 한 번이 트레이스 하나로 보인다. 실험 항목 자체는 `langfuse-prompt-experiment` 환경에 쌓인다.

교안이 "실패 판정의 판단 이유를 꼭 읽으라"고 한 것은 **심사가 기준대로 판정했는지** 보기 위해서다. 답만 봐도 이 셋은 통과 조건을 안 지킨 게 분명하지만, 이유를 읽어야 심사가 말투나 길이를 보고 있지 않다는 것까지 확인된다.

### 미룬 것 — 심사 다듬기 (나중에)

심사도 평가 대상이다. 느슨한 심사는 **실패를 통과로 놓쳐서**, 지시문이 나빠져도 점수가 그대로다. 쓸 수 있는 기준은 일치율 90% 이상, 놓친 실패(사람은 실패인데 심사는 통과) 거의 없음.

나중에 할 세 가지:

1. **사람 라벨과 일치율** — 두 실행의 답 24개에 심사 판정을 보기 전에 직접 통과/실패를 붙이고 비교한다. 단, H01·H02·H06·H08·H12 의 판정은 이미 봤으므로 그 다섯은 오염됐다. 깨끗한 7항목(H03, H04, H05, H07, H09, H10, H11)의 14개만 쓰거나, 일치율을 두 벌로 낸다.
2. **기준 문장을 줄인 심사와 비교** — 예시 세 줄을 빼거나 판정 기준을 한 줄로 줄인 심사를 하나 더 만들어 같은 실행에 건다. 어느 문장이 어떤 답을 잡고 있었는지 보인다.
3. **경계 사례** — 지금 지시문에는 금요일·월요일만 적혀 있다. 아래 둘은 판정이 갈린다.

| 경우 | 정할 것 |
| --- | --- |
| 공휴일이 **목요일** (금요일 휴가 내면 나흘) | "금요일 쉬면 나흘"을 제안해야 통과인가 |
| 공휴일이 **토요일** (주말과 겹쳐 쉬는 날이 안 늘어남) | 대체공휴일을 말해야 통과인가 |

같은 경계 항목을 두 번 돌려 판정이 흔들리면 그게 기준 문장의 빈 곳이라는 신호다.

## 섹션 4 — 프롬프트 관리와 실험

### router 프롬프트를 코드 밖으로

`app/router.py` 의 `router_prompt` 를 Langfuse 프롬프트 관리로 옮겼다.

| 항목 | 값 |
| --- | --- |
| 이름 | `router` |
| 변수 | `{{tools}}` 하나 |
| 버전 1 | 지금 코드의 문장. 라벨 `production`, `staging` |
| 버전 2 | 규칙 두 줄 추가. 라벨 `staging` 으로 옮김 |

바꾼 파일:

- `app/tracing.py` — `prompt(name, label=None)`. ENV 가 `production` 이면 `production` 라벨, 아니면 `staging` 라벨. 못 가져오면 `None`
- `app/router.py` — `tool_lines()`, `router_prompt(tools=None)`, `load_prompt(label=None)` 분리. `model_choose(..., system=None)`. `choose()` 에서 generation 에 프롬프트 연결
- `scripts/upload_router_prompt.py` — 새 파일
- `scripts/eval_tools.py` — `--label` 옵션

**손으로 옮겨 적지 않았다.** 업로드 스크립트가 코드의 함수를 그대로 부른다.

```python
text = router_prompt("{{tools}}")
```

가져온 문장이 코드의 기본 문장과 글자까지 같은 것을 확인했다. 베껴 적으면 실험 결과가 달랐을 때 지시문 탓인지 옮겨 적은 탓인지 가릴 수 없다.

#### 폴백 확인

`LANGFUSE_BASE_URL` 을 틀린 주소로 두고 돌렸다.

```
Error while fetching prompt 'router-label:staging': [Errno 11001] getaddrinfo failed
{"severity": "WARNING", "message": "Langfuse 프롬프트를 가져오지 못해 코드의 기본 문장을 씁니다", ...}
코드 기본 문장으로 돌아갔나: True
```

#### 짚어 둔 것 — MAX_TOOLS

`router_prompt` 는 `f"- 꼭 필요한 도구만 최대 {MAX_TOOLS}개 고른다"` 로 숫자를 박아 넣는다. Langfuse 문장에는 `최대 2개` 로 리터럴이 됐다. 코드에서 `MAX_TOOLS` 를 바꿔도 프롬프트는 안 따라간다.

실제 개수 제한은 `choose()` 의 `result.tools[:MAX_TOOLS]` 가 걸어서 동작은 안 깨진다. 변수로 뺄 수도 있었지만 교안 예시와 글자가 달라져 실험 비교가 흐려진다.

### 실험 — v1 과 v2 를 두 번씩

도구 선택은 `[지금]` 과 `[달력]` 을 채우고 도구 목록을 넣는 서비스 코드(`model_choose`)를 거쳐야 해서 화면 실험으로 못 돌린다. `scripts/run_tool_experiments.py` 를 만들어 SDK 의 `run_experiment` 에 실행할 작업과 코드 평가자를 넘겼다.

```
router-production-v1-1: args 34/41 · tool 38/41
router-production-v1-2: args 35/41 · tool 39/41
router-staging-v2-1:    args 34/41 · tool 37/41
router-staging-v2-2:    args 32/41 · tool 39/41
```

**전체 숫자만 보면 버전 2 가 낫지 않다.** 항목별로 봐야 한다.

### 결과 — 고쳐진 것과 고쳐지지 않은 것

| 항목 | v1 | v2 | 판정 |
| --- | --- | --- | --- |
| T26 다음 공휴일 | X, O | **O, O** | 기간 규칙이 먹었다 |
| T34 시험 전날 | X, X | O, X | 2번 중 1번. 여전히 불안정 |
| T10 미세먼지 하소연 | O, O | **X, X** | 회귀 |
| T15 모레 제주 날씨 | O, O | **X, X** | 회귀 |
| T20, T31, T37 | O, O | 한 번만 X | 흔들림 |

**T26 은 지시문으로 고쳐졌다.** "다음 공휴일"을 어떻게 해석할지의 문제라서, 해석 방법을 문장으로 알려 주면 모델이 따른다. 다만 v1 도 두 번 중 한 번은 통과했으므로 2회 비교로는 "확실히 고쳐졌다"까지 말하기 이르다.

**T34 는 고쳐지지 않았다.** 금요일이 며칠인지 찾아 하루를 빼는 것은 **계산**이고, 계산 방법을 문장으로 적어도 모델은 자주 틀린다.

```
v1-1  due_at 2026-10-14T21:00   (정답 10-15)
v1-2  due_at 2026-10-14T21:00
v2-1  due_at 2026-10-15T21:00   맞음
v2-2  due_at 2026-10-14T21:00
```

### 회귀 — 전날 규칙이 중복 호출을 불렀다

T10 과 T15 는 **두 실행 모두** 나빠졌다. 한 실행에서만 나오면 흔들림이지만, 둘 다면 규칙이 다른 메시지에 영향을 준 것이다.

```
T10  "미세먼지 때문에 비염이 심해졌어"   (도구를 쓰면 안 되는 하소연)
     v2 → get_air_quality(10-12) + get_air_quality(10-13)   두 번

T15  "모레 제주 여행 가는데 날씨 괜찮을까"  (정답 get_weather day=2)
     v2 → get_weather(10-14) + get_weather(10-15)           두 번
```

둘 다 **같은 도구를 두 번** 골랐다. 어제 `get_air_quality` 와 `get_holidays` 에서 본 유형 4 와 같은 모양이다.

새로 넣은 둘째 규칙이 범인으로 보인다.

```
- '시험 전날', '출발 이틀 전'처럼 어떤 날을 기준으로 앞뒤를 말하면,
  먼저 [달력]에서 기준이 되는 날의 날짜를 찾고 거기서 날짜를 빼거나 더한다.
```

"앞뒤"라는 말을 날짜 **범위**로 읽어, 기준일과 그 앞뒤 날짜를 각각 조회하게 만든 것으로 보인다. T15 의 10-14 와 10-15, T10 의 10-12 와 10-13 이 그 모양이다.

**고치려던 실패는 안 고쳐지고, 멀쩡하던 항목 둘을 망가뜨렸다.** 이것이 회귀 확인을 고친 항목만 보지 않고 41개 전체로 돌리는 이유다.

### v3 — 회귀를 되돌리려다 더 나빠졌다

v2 의 전날 규칙 **한 줄만** 고쳤다. "앞뒤"를 범위로 읽던 것을 막고, 본 적 있는 실패 모양을 직접 금지했다.

```
v3: - '시험 전날', '출발 이틀 전'처럼 어떤 날을 기준으로 앞뒤를 말하면,
       [달력]에서 기준이 되는 날을 찾고 거기서 날짜를 빼거나 더해 날짜 하나만 정한다.
       기준이 된 날과 계산한 날을 함께 고르지 않고, 같은 도구를 날짜만 바꿔 두 번 고르지 않는다.
```

```
v1  args 34, 35 · tool 38, 39
v2  args 34, 32 · tool 37, 39
v3  args 30, 28 · tool 36, 32      ← 가장 나쁨
```

| 항목 | v1 | v2 | v3 |
| --- | --- | --- | --- |
| T10 미세먼지 하소연 | O O | X X | **X X** |
| T15 모레 제주 날씨 | O O | X X | X O |
| T26 다음 공휴일 | X O | O O | O X |
| T34 시험 전날 | X X | O X | **X X** |
| T19, T22, T28 | 섞임 | 섞임 | **X X** |

**금지 문장이 듣지 않았다.** T10 은 "같은 도구를 날짜만 바꿔 두 번 고르지 않는다"를 그대로 적었는데도 v3 두 번 모두 `get_air_quality` 를 두 번 골랐다.

```
T10  v1  tools []                                        ← 맞음
     v2  get_air_quality(10-12) + get_air_quality(10-13)
     v3  get_air_quality(10-12) + get_air_quality(10-13)  ← 금지해도 그대로
```

**금지가 오히려 새 중복을 만들었다.** T26 은 v2 에서 `get_holidays(args={})` 하나로 깔끔했는데, v3 에서는 두 번 고른다.

```
T26  v2-1  get_holidays({})                                        ← 깔끔
     v3-1  get_holidays({}) + get_holidays(12-01~12-31)            ← 통과하지만 중복
     v3-2  get_holidays({}) + get_holidays(10-12~10-31)            ← 실패
```

"두 번 고르지 말라"고 적자 **두 번 고르는 선택지를 떠올린** 모양이다. 하지 말라는 말을 적으면 그 행동이 가능한 것으로 읽히는 흔한 함정이다.

**T34 는 v3 에서 두 번 다 틀렸다.** v2 에서 한 번 맞은 것은 흔들림이었다.

```
v1-1 10-14   v1-2 10-14   v2-1 10-15   v2-2 10-14   v3-1 10-14   v3-2 10-14
```

여섯 번 중 한 번만 맞았다. 정답은 10-15 다.

### 결론 — 프롬프트로 고칠 것과 코드로 고칠 것

| 실패 | 결과 | 고칠 곳 |
| --- | --- | --- |
| 다음 공휴일 기간이 좁음 (T26) | v2 에서 고쳐짐 | **프롬프트** — 말의 뜻을 해석하는 일 |
| 시험 전날 날짜 (T34) | v1·v2·v3 여섯 번 중 한 번만 맞음 | **코드** — 날짜를 더하고 빼는 계산 |
| 같은 도구 중복 호출 (T10, T15) | 금지해도 안 고쳐지고 새 중복까지 생김 | **코드** — `choose()` 에서 중복 제거 |

세 버전을 두 번씩 돌린 뒤에야 이 표를 쓸 수 있다. 한 번씩 돌렸다면 v2 의 T34 통과를 보고 "고쳐졌다"고 했을 것이다.

`production` 라벨은 **버전 1 그대로 둔다.** v2 도 v3 도 전체로는 v1 보다 낫지 않다. `staging` 라벨은 v1 로 되돌린다 — 라벨만 옮기면 되고 코드 배포는 없다.

### 코드로 고치기

실험이 가른 대로 두 가지를 코드로 옮겼다. 프롬프트는 `production` 라벨의 버전 1 그대로 두고 쟀다.

**하나 — 같은 도구를 같은 인자로 두 번 고르면 하나만 남긴다** (`app/router.py` `choose`)

```python
key = (tool["name"], json.dumps(tool["args"], sort_keys=True, ensure_ascii=False))
```

이름만으로 지우지 않았다. "서울이랑 부산 날씨"는 `get_weather` 를 두 번 부르는 것이 맞다. 어제 본 중복은 인자까지 같았다.

**둘 — 기준일에서 날짜를 빼는 계산을 코드가 한다** (`app/router.py` `fix_relative_due`)

`app/when.py` 에 이미 `parse_when` 이 있었다. 모델이 그것을 안 쓰고 직접 계산하던 것이 문제였다.

```
모델이 하는 일   "금요일" 과 "밤" 을 읽기
코드가 하는 일   금요일의 날짜 찾기(parse_when) → 하루 빼기
```

`'전날'`, `'이틀 전'` 같은 **빼는 표현이 있을 때만** 덮어쓴다. 파서가 기준일을 못 읽으면 모델이 낸 값을 그대로 둔다. 무턱대고 덮어쓰면 멀쩡하던 항목이 깨진다.

#### 결과

```
고치기 전 (v1)   인자까지 34/41,  35/41
고친 뒤          인자까지 39/41,  36/41
```

**T34 가 두 실행 모두에서 사라졌다.** 고치기 전에는 여섯 번 중 다섯 번 틀렸다.

남은 실패:

| 항목 | 1회차 | 2회차 | 성격 |
| --- | --- | --- | --- |
| T16 `지금 밖에 추워?` | 실패 | 실패 | 날씨를 에둘러 묻는 말을 못 알아봄 — 해석 문제 |
| T33 `다음 주 월요일 아침` | 실패 | 실패 | `아침` 을 09:00 으로. 지시문에 08:00 이라 적혀 있는데도 |
| T19, T26, T38 | 통과 | 실패 | 흔들림. T26 은 기간 규칙이 없는 v1 이라 예상된 실패 |

T33 은 **같은 방법으로 코드가 고칠 수 있다.** `when.parse_when` 의 `PARTS` 가 이미 `아침 → 08:00` 을 안다. 지금은 빼는 표현이 있을 때만 덮어쓰므로 T33 은 손대지 않는다.

흔들림은 여전히 크다(39 와 36). 두 번으로는 부족하다는 뜻이고, 다음에 잴 때는 세 번씩 돌리는 편이 낫다.

### 이어서 고치기 — 시각 보정과 v4

**코드 — '아침' 같은 때 표현의 시각을 맞춘다** (`app/router.py` `fix_time_of_day`)

`when.PARTS` 가 `아침 8, 점심 12, 저녁 19, 밤 21` 을 갖고 있는데 모델은 `아침` 을 09:00 으로 내곤 했다. **시각만 바꾸고 날짜는 건드리지 않는다.** 날짜를 잘 읽은 항목이 깨지지 않게 하려는 것이다. 몇 시라고 분명히 말한 메시지(`3시`)는 손대지 않는다.

**프롬프트 v4 — 기간 규칙만** (v1 + 한 줄)

v2 에서 회귀를 부르던 전날 규칙은 뺐다. 그 일은 이제 코드가 하므로 프롬프트에 둘 이유가 없다.

#### v1 과 v4 를 세 번씩

```
v1  args 39, 37, 38   (평균 38.0)
v4  args 37, 37, 35   (평균 36.3)
```

평균만 보면 v4 가 낮다. 항목별로 보면 다른 그림이 나온다.

| 항목 | v1 | v4 | |
| --- | --- | --- | --- |
| T26 다음 공휴일 | **X X X** | **O O O** | 기간 규칙이 확실히 일했다 |
| T33 아침 08:00 | O O O | O O O | 코드 시각 보정. 고치기 전에는 두 번 다 실패 |
| T34 시험 전날 | O O O | O O O | 코드 날짜 계산 |
| T15 모레 제주 | O X X | O O O | v4 가 더 안정적 |
| T16 에둘러 묻는 날씨 | X X X | X X X | 아직 손대지 않음 |

**세 번 다 틀리는 항목**으로 세면 뒤집힌다.

```
v1  T16, T26  두 개      → 천장 39/41
v4  T16       하나       → 천장 40/41
```

v4 의 나머지 실패는 T10, T13, T18, T20, T21, T22, T23, T28, T37, T38 로 **넓게 흩어져 있고 대부분 세 번 중 한 번**이다. 특히 `v4-3` 한 실행에 몰려 있다(35/41). v1 의 실패는 T16·T26 에 **집중**돼 있다.

읽는 법: v4 는 노린 항목(T26)을 세 번 다 잡았고 **세 번 다 틀리는 회귀는 없다**. 평균 차이는 흩어진 1회성 실패와 `v4-3` 한 실행 때문이다. 세 번으로도 이 둘을 완전히 가르지는 못한다. 다만 "v4 가 구조적으로 나쁘다"는 근거는 없다.

**배포 판단**: 노린 실패를 고쳤고 구조적 회귀가 없으므로 v4 를 `production` 으로 올릴 만하다. 평균이 낮은 것이 마음에 걸리면 각 다섯 번씩 더 돌려 확인한 뒤 올린다.

### 다섯 번씩 — v4 를 올리면 안 되는 이유

세 번으로는 "흩어진 잡음"으로 보이던 것이 다섯 번에서 방향을 드러냈다.

| 항목 | v1 실패 | v4 실패 | |

| T19 그럼 모레는? | 3/5 | 2/5 | 비슷 |

기간 규칙은 `get_holidays` 이야기만 하는데 **다른 도구에까지 호출을 덧붙인다.** v2, v3, v4 세 버전 모두 같은 모양이었다.

> **이 지시문에 날짜·기간 규칙을 더하면 도구를 덧붙인다.** 세 번 반복된 패턴이다.

### 걸린 것 — 실행 이름을 재사용했다

소량 시험(`--limit 5`)을 `router-staging-v2-1` 이라는 같은 이름으로 돌려서, 그 실행에 항목이 46개 들어갔다(41 + 5). Langfuse 는 같은 `run_name` 이면 한 실험으로 묶는다.

두 번째 배치에서도 같은 이름을 다시 써서 앞 배치와 섞였다. 항목별 비교를 시각으로 걸러 겨우 가렸다. `scripts/run_tool_experiments.py` 의 `run_name` 에 시각을 붙여 막았다.

```python
run_name = f"router-{label}-v{version}-{n} {stamp}"
```
